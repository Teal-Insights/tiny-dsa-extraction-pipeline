Binding schema and conventions:
- Before authoring YAML, load the bundled JSON Schema from excel-grapher and use it as the authoritative field and shape reference:

  from importlib.resources import files

  schema_text = (
      files("excel_grapher.series_bindings")
      .joinpath("series_binding.schema.json")
      .read_text(encoding="utf-8")
  )

- Use schema_version: 1.13.0.
- Create a bindings/ directory with four files (empty `series: []` placeholders are fine during bootstrap):
  - inputs.bindings.yaml for public input setters.
  - outputs.bindings.yaml for public output compute functions.
  - internals.bindings.yaml for internal formula-cell triangulation (`internal: {}`).
  - constants.bindings.yaml for reader-only graph leaves (`constant: {}`) that should emit `read_*` without `set_*` / `compute_*`.
- Use one series[] entry per logical public input, output, internal formula series, or constant leaf group.
- Use layout: scalar for one-cell inputs and layout: row_series for one-row time series.
- Use structure.measure.concept: OBS_VALUE with bind.kind: data_cell.
- Use key fields only for record matching. For row time series, use TIME_PERIOD from the column header row. For scalar parameters, use keyless bindings (`key: []`) and keep PARAMETER in series_context. For keyed tables, use the header that identifies each record as the key.
- Give every dimension an explicit id. The id names the dimension itself; concept names the SDMX-style meaning category it references. They match unless two dimensions in one series share a concept (e.g. a projection axis and a reference period both on TIME_PERIOD), in which case give each dimension a distinct id. Record fields, key entries, series_context, and internals-refactor parameters use the effective id. Parameter names are derived from the effective id (e.g. PROJECTION_PERIOD → projection_period). Concept-only keys are a legacy fallback only when the concept uniquely identifies one dimension.
- Example when two dimensions share TIME_PERIOD:

  dimensions:
    - id: PROJECTION_PERIOD
      concept: TIME_PERIOD
      role: key
      scope: cell
      bind: {kind: column_header, header_row: 5, read: int}
    - id: REFERENCE_PERIOD
      concept: TIME_PERIOD
      role: key
      scope: cell
      bind: {kind: value_map, values: {0: C:G}, read: int}
  key: [PROJECTION_PERIOD, REFERENCE_PERIOD]
- When an internal formula's operands vary independently along one concept (e.g. bilateral flows reading a reporter series and a counterpart series), declare a distinct dimension id for each role on the internal series that binds the formula cells (e.g. REF_AREA plus COUNTERPART_REF_AREA, both concept REF_AREA). Without distinct ids such clusters are skipped as operand_level_variation_unsupported; with them the refactor uses the dimension-aware contract (see bindings/README.md).
- Sparse column_header / row_label cells need fill: true when labels sit only on the first column/row of a group (e.g. a year above a Base/Alt/Gap measure triplet, with blanks above Alt and Gap). Without fill, blank labels raise bind_resolution_failed and resolution ok=False even if validate_series_bindings looked fine.
- Do not bind one contiguous rectangle across mixed measure columns when the public key is only (SCENARIO, TIME_PERIOD) or similar. Prefer one shard per measure (or per milestone) column, or a richer key that includes the measure dimension (as internals often do). See bindings/README.md and templates/binding-pattern-measure-shards.example.yaml.
- When sharding outputs/inputs, share the same compute_/set_ name only when export should merge complementary slices into one public function (e.g. Gap milestone columns). Uniquify compute_/set_ names when each shard is a distinct scenario or engine path; colliding shared names merge definitions and can leave most paths unreachable in the exported library.
- workbook_config.TARGETS (and overlapping internal data ranges) must cover every bound data cell. Widening a binding past the previous target end requires widening TARGETS / internals so those cells stay on-graph.
- Add input.setter.name values matching set_[a-z][a-z0-9_]* for input series.
- Add output.compute.name values matching compute_[a-z][a-z0-9_]* for output series.
- Add internal series with `internal: {}` for formula cells that need concept-key triangulation during internals refactor. Internal series do not generate public setter or compute code.
- Add constant series with `constant: {}` for graph leaves that formulas should read via `read_*` without a public `set_*`. Optional `constant.reader.name` overrides the default `read_<series_id>`. Constant bindings require leaf overlap (`non_leaf_constant_overlap` / `no_leaf_constant_targets` otherwise) and are mutually exclusive with input/output/internal. Do not confuse the constant direction with bind.kind: constant (a fixed structure scalar). Leaf classification via Literal[...] CONSTRAINTS is separate: it seeds CONSTANTS vs DEFAULT_INPUTS; a constant binding is what rewrites xl_cell to read_*.
- Do not bind structurally empty cells (INDEX/MATCH padding, NPV/SUM year-window overflow, unused ladder copies, separator rows). Those belong in workbook_config.BLANK_RANGES (sheet-qualified A1 rectangles passed to graph build, FormulaEvaluator, and codegen), not inputs/constants. Do not put user-fillable yellow slots in BLANK_RANGES.
- Include useful series_context and UNIT_MEASURE attributes where they clarify records.
- Do not include internal engine calculations or read-only lookup/profile data as public API bindings unless the guide says downstream users should set or read them directly.
